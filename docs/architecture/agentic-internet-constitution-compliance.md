## Authority map

This proposal does not change the authority assigned to another repository or
domain:

| Question | Authority |
|---|---|
| Constitutional direction and institutional limits | The exact ratified Constitution and amendment record, if and when adopted for OpenFox's declared scope |
| Shared Intent, Agreement, authority, semantic-action, Receipt, dispute, and settlement meaning | The applicable versioned normative specification in `tosnetwork/tos-service-spec` |
| Canonical encoding, verification, resolution, and reference behavior | `tosnetwork/tos-service-protocol`, subordinate to the normative specification |
| OpenFox discovery, interpretation, economic assessment, capability matching, local policy, execution coordination, and owner projections | The exact OpenFox implementation and configuration, bounded by accepted protocol authority |
| TOS finality, account, asset, contract, and settlement facts | Independently verified finalized TOS state under the applicable network and consensus rules |
| External or direct payment | The evidence and residual-risk rule named by the exact Agreement; it is not TOS-finalized state |

An OpenFox journal, report, model output, Gateway row, Carrier cursor, mobile
projection, or capability catalog entry is never a substitute for normative or
finalized authority.

## Interim non-derogable controls

Until the target admission and promotion mechanisms are implemented and their
gates pass, all OpenFox operation covered by this proposal MUST obey these
interim controls:

1. `evolution.mode=apply` MUST NOT be enabled for autonomous earning,
   production, or any workflow capable of a Consequential Action. A broad
   owner configuration is not a candidate-specific promotion decision.
   `observe`, or `draft` followed by independent review, is the maximum allowed
   evolution posture for those workflows.
2. A generated or acquired Skill remains a proposal. It MUST NOT be loaded
   into consequential work until a separate `PromotionAuthority` record binds
   the exact candidate, evidence, approving authority, scope, expiry, and
   rollback path.
3. Existing installed third-party Skills and configured MCP servers MUST be
   treated as `UNVERIFIED_LEGACY` for this target architecture until an exact
   version is re-admitted. Prior installation, connectivity, popularity, or
   successful use does not grandfather trust.
4. No real BTC, USDT, fiat, securities, third-party custody, or unrestricted
   owner key may enter these campaigns. Synthetic or test-network value does
   not prove legal, custody, accounting, public-network, or production safety.
5. A campaign result MUST NOT change authority, permissions, budget, custody,
   network access, or production exposure directly. It may only propose one
   bounded change for a separate owner decision.
6. A TOS-backed settlement path MUST remain `BLOCKED` unless the exact selected
   protocol/profile version, network, adapter, signer and custody boundary,
   conformance evidence, and required finality view all pass their own current
   release gates.

## PromotionAuthority minimum record

The future deterministic promotion gate MUST bind at least:

- candidate kind, stable identity, origin, publisher, exact version and digest;
- source learning records or acquisition decision, data classification, and
  confirmation that no prohibited or Agreement-bound data entered the
  candidate;
- frozen evaluation manifest, retained alternative, unseen task commitment,
  primary and harm metrics, result, uncertainty, exclusions, and independent
  verifier;
- requested tools, filesystem, network, credential, data, budget, and task
  scope before and after promotion;
- owner-policy revision, approving human or accountable authority, decision
  time, expiry, activation condition, and revocation path; and
- rollback artifact, compatibility effect, in-flight-work treatment, and
  evidence-retention rule.

The candidate, generating model, task content, registry, MCP server, and
automatic success threshold MUST NOT issue or satisfy this authority. A
promotion that changes shared protocol meaning must instead enter the
appropriate normative-specification process.

## Protocol-versus-product boundary

| Surface | May remain OpenFox-local | Must move through normative protocol governance before an interoperability claim |
|---|---|---|
| Capability policy | Owner preferences, approved source list, local ranking, local sandbox profile | Any cross-party capability identity, attestation, delegation, or conformance object required for other implementations |
| Owner control | Local UI layout, notifications, derived dashboards, local scheduling | Any shared command, approval, revision, revocation, or portable event semantics presented as an Agentic Internet or TOS protocol |
| Reports | Local Markdown layout, private analysis, owner-specific classification policy | Any shared signed report, Receipt, accounting, or settlement assertion relied on across parties |
| Earning strategy | Local search, interpretation, pricing recommendation, Skill choice | Intent, Agreement, authority, evidence, semantic-action, Receipt, dispute, and settlement meanings |

If a local object crosses an authority boundary or is required for independent
interoperation, it needs a public versioned schema, domain separation,
positive and negative vectors, compatibility rules, licensing, and independent
implementation evidence in the proper standards repository.

## Remaining blockers

The provisional status cannot become `CONFORMANT`, and no target capability
may be called production-ready, until evidence closes the applicable blockers:

- constitutional ratification and an exact OpenFox adoption scope, compliance
  owner, review cycle, and Major Surface ownership record;
- implementation and tests for capability identity, admission, permissions,
  revocation, controlled updates, and `PromotionAuthority`;
- runtime enforcement of the consequential-workflow `apply` prohibition until
  an exact `PromotionAuthority` is present;
- implementation and tests for the maintained reports, durable owner
  projection, shared owner-command authority, and both mobile clients;
- formal, pre-registered, and independently reproduced Campaign 1--6 evidence
  in the required order, including Gate S and Gate M where applicable; the
  completed local rehearsal does not satisfy this blocker;
- normative review for every shared authority or interoperability object;
- public-testnet and independent production acceptance for any selected
  TOS-backed settlement profile whose current release record still requires it;
- independent security review of capability supply, MCP sandbox and
  authentication, owner commands, mobile sessions and approval, report privacy,
  custody, and recovery;
- real iOS and Android device evidence plus cross-host and independent-operator
  evidence; and
- external, arm's-length, finalized payment and repeat-use evidence before any
  claim of profitable autonomous adaptation.

This record must be revised rather than silently reinterpreted when a blocker
closes, a scope changes, a constitutional version is ratified, or evidence
contradicts a current claim.
